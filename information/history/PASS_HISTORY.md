**Pass 156z9u (Stage B-2c off-switch — `engine.inline_search_enabled`):**

- **`EnigmaEngine.inline_search_enabled: bool = True`** in [inference.py L_init_common](enigma_engine/core/inference.py) — initialised after `last_search_queries_per_prompt`. Default True so existing callers see no behaviour change (Pass 156z9d's always-on observability is preserved). Set to False to suppress the post-gen scan, the WARNING, and the future B-3 trigger.
- **`_record_search_emissions` early-return** in [engine_generation.py L326](enigma_engine/core/engine_generation.py): `if not getattr(self, "inline_search_enabled", True): self.last_search_queries = []; return`. The `getattr(..., True)` default keeps stub-built test instances (and any legacy caller that pre-dates the flag) working without a forced migration. Off-path (flag False) is silent — no log, no scan, no exception — matching the loud-on-real-issue / silent-on-normal-path discipline.
- **Reset to `[]` on disable.** When the flag is False the helper resets `last_search_queries` to the empty list rather than leaving stale data from a previous turn. This is the contract callers expect: "queries from the most recent turn or empty." A user who disables mid-session must NOT see ghosts from before the toggle.
- **4 new tests** in `TestStageB2SearchEmissionRecording` and `TestStageB2EngineWiring` ([tests/test_chat.py](tests/test_chat.py)):
  - `test_off_switch_skips_scan_and_resets_list` — flag False + previous-turn data + emission text → list cleared, no WARNING. Adversarial: an implementation that scans-then-discards would still log the WARNING; this test gates the WARNING suppression.
  - `test_off_switch_default_is_on` — explicit `flag=True` records normally. Sibling-parity gate to make sure the early-return only fires when explicitly disabled.
  - `test_off_switch_missing_attribute_defaults_to_on` — no attribute set → records normally. Locks the `getattr(..., True)` contract for legacy callers.
  - `test_init_common_sets_inline_search_enabled` — structural test that `_init_common` source contains `self.inline_search_enabled` AND `True` on the same line. Without this, the off-switch is reachable only via manual user assignment — partial feature.

- **Author's-lens self-audit (§1 #19 six-question lens):**
  1. *Would I write it this way?* Yes — single-flag opt-out with default-on is the minimum surface area for the contract.
  2. *Connected to what?* Same 3 wire-sites that already exist (`_record_search_emissions` is called from `engine_chat.py:605`, `:798`, `:832`). No new wire-sites needed because the flag gates the helper itself, not each call site.
  3. *Connections that should exist but don't?* GUI surface for the flag (a checkbox on the chat config page). Logged below as a future small slice. Not strictly part of B-2c — the flag is library-level; GUI exposure is its own pass.
  4. *Logic-eye?* Docstring claim "skip scan + reset list + suppress WARNING" matches code: early-return BEFORE the scan, BEFORE the WARNING, after resetting `last_search_queries = []`. Test `test_off_switch_skips_scan_and_resets_list` adversarially gates all three.
  5. *Claim-vs-test?* The off-switch test asserts `last_search_queries == []` AND `not any("Stage B-2" in r.message ...)` — checks both consequences in one test, so a regression that suppresses the scan but forgets to reset, OR that resets but logs anyway, fails loudly.
  6. *Sibling-boundary sweep?* `_record_search_emissions` is the single helper called from all 3 generation paths. Gating at the helper is one site that closes the family. No `_generate_with_vision` / `speculative_generate` / `medusa_generate` / `lookahead_generate` direct-call sites for this helper (those decode through `_generate_text` which then calls `_record_search_emissions` once at its return path) — verified by grep `_record_search_emissions` across `enigma_engine/core/`.

**Pass 156z9r (Q3_K GGUF dequant):**

- **`dequantize_q3_K(data, shape)`** in [enigma_engine/core/gguf_dequant.py](enigma_engine/core/gguf_dequant.py) — 110 B/super-block: 32 (`hmask`, 256 × 1 high-bits packed 8-per-byte) + 64 (`qs`, 256 × 2 low-bits packed 4-per-byte) + 12 (`scales`, 16 × 6-bit signed bit-packed) + 2 (fp16 `d`). Per-sub-block: `signed_scale = scale_packed - 32` (range [-32, 31]), `dl = d * signed_scale`. Per-element: `q_low = (qs_byte >> shift) & 0x03`, `q_full = q_low - (hm_bit_set ? 0 : 4)` (centers [0, 7] → [-4, 3]). Loop over `is = 0..15`: `half = is // 8`, `j = (is // 2) % 4` (shift = `2*j`), `nibble_half = is % 2`. Vectorised across `n_blocks` per sub-block. Zero-block guard returns `torch.zeros(shape, dtype=torch.float32)` matching siblings.
- **6-bit scale stitch unpack** uses formulas mirroring the C `aux[]` trick: `low_byte_idx = (is % 4) + 4 * ((is // 4) % 2)`, `low_shift = 4 if is >= 8 else 0`, `high_byte_idx = 8 + (is % 4)`, `high_shift = 2 * (is // 4)`. The 4-bit low nibble cycles through `scales[0..7]` (low-half) then `scales[0..7]` (high-nibble half); the 2-bit high stitch lives in `scales[8..11]` and shifts through 4 bit-positions across the 16 sub-blocks. Each scale_packed value combines to a 6-bit unsigned int; `- 32` converts to signed.
- **hmask routing.** The same hmask bit is consumed by TWO consecutive sub-blocks (low-half-of-hmask for is even, high-half for is odd) before the bit position advances. So `bit_pos = is // 2`, `hmask_off = nibble_half * 16`. Same 32 hmask bytes are reused across both halves — only the bit position changes.
- **Constant `GGML_TYPE_Q3_K = 11`** + dispatcher branch: collapses `(Q2_K, Q4_K, Q5_K, Q6_K)` into `(Q2_K, Q3_K, Q4_K, Q5_K, Q6_K)` with `bytes_per_block = 110` for Q3_K. - **What shipped (Q4_1 / Q5_0 / Q5_1):** three new public dequantizers in [enigma_engine/core/gguf_dequant.py](enigma_engine/core/gguf_dequant.py), all vectorized via numpy, all matching the ggml-quants.c reference layout: byte j of `qs` holds the low nibble for element j (low half 0..15) and the high nibble for element j+16 (high half 16..31). Q4_1 dequantizes as `q*d + m` (unsigned, 20-byte block: fp16 d + fp16 m + 16 qs bytes). Q5_0 combines low-nibble | (5th bit from `qh` u32 << 4), then `(q-16)*d` signed (22-byte block: fp16 d + 4 qh bytes + 16 qs bytes). - **Sibling-sweep finding — Q4_0 layout bug fixed:** while implementing the three siblings to match ggml's two-halves convention (`y[i*qk + j + 0] = x0*d`, `y[i*qk + j + qk/2] = x1*d`), spot-checked the existing `dequantize_q4_0` and found it using the WRONG layout: `output[i*32 + j*2] = scale*low; output[i*32 + j*2 + 1] = scale*high` — interleaved nibble layout instead of two-halves. Cross-referenced against [ggml/src/ggml-quants.c `dequantize_row_q4_0`](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-quants.c) (web fetch this pass to confirm convention against current upstream): convention is universally `y[j+0]=x0*d, y[j+qk/2]=x1*d` across Q4_0/Q4_1/Q5_0/Q5_1. The existing test `test_dequantize_q4_0_values` passed because it used `bytes([0xFF]*16)` — every byte = same value, layout-blind; same for `test_dequantize_q4_0_zero_scale`. So this has been silently mis-permuting every Q4_0 row read from a real GGUF since the function shipped. **Why this matters:** anyone loading a real Q4_0-quantized GGUF (Llama-2 / Mistral 7B / older quants) through `gguf_loader.py` got a model with every weight tensor's elements 0..31 of each 32-element block scrambled — element 0 came from byte 0's low nibble (correct in both layouts), but element 1 came from byte 0's high nibble (in the broken layout) instead of byte 1's low nibble (correct). Outputs would be garbage but loadable; the bug is invisible without reference comparison. Fix: rewrote `dequantize_q4_0` to vectorized numpy mirroring the new siblings — block reshape, `(qs & 0x0F).astype(int16) - 8` for low half (elements 0..15), `((qs >> 4) & 0x0F).astype(int16) - 8` for high half (elements 16..31), single multiply by `d[:, None]`. New `test_dequantize_q4_0_layout` constructs a block with `byte 0 = 0x91` (low=1, high=9) and `byte 5 = 0xC3` (low=3, high=12) and asserts elements `[0]=-7, [16]=1, [5]=-5, [21]=4, [1]=-8, [17]=-8` — would have failed against the old interleaved code, passes against the new two-halves code, will fail again if anyone reverts the layout. The Top-9 #2 sibling-boundary sweep rule is exactly what caught this — touched one site of a multi-site contract family, grepped the family, found a sibling that didn't match the contract, fixed in the same pass. Without the sweep this would have shipped a "dequant family done" stamp while leaving Q4_0 broken.

Per Rule #18 (named overhaul scope) and Top-9 #2 (sibling-sweep mandatory), inside the GGUF-dequant-family scope, fixing a sibling that doesn't match the contract is the slice's job. Splitting it across two passes would have let a known bug ship for one more cycle and broken the "fix the family in one pass" discipline. The fix is small (one function body rewrite + one test) and localized; no caller signature changed.

- **Templates ship for `chatml` (covers Qwen2/Qwen3/ChatGLM3+ and most Open-source ChatML-trained models, including the user's existing `qwen3:8b` Ollama default) and `llama3`. `--template custom` supports user-supplied prefix/markers via three flags. `_resolve_magpie_template` raises `ValueError` naming the missing flag at parse time, NOT after the run wastes prompts — a misconfiguration cost is upper-bounded at zero.

- **`_parse_magpie_completion(raw, template) -> tuple[str, str]`:** splits on the user→assistant marker, strips the assistant_end marker if the model emitted it (some servers ignore the `stop` hint and run to the natural end-of-turn), raises `RuntimeError` with descriptive messages on three real failure modes:
  - **Marker missing** — wrong template for model, or temperature caused early stop. The fail loud is critical because without it, the entire raw model output would be written as the "instruction" with an empty completion, polluting the corpus with junk that then trains the student to emit raw chat markers.
  - **Empty instruction** — model emitted the assistant marker without first proposing a question. Empty prompts in JSONL are useless training rows.
  - **Empty answer** — model proposed an instruction but ran out of `max_tokens` before answering. Truncated answers as training data teach the student to stop mid-thought.

- **`MagpieClient.ask_pair(*, max_tokens, temperature, top_p) -> tuple[str, str]`:** stdlib-only HTTP client (mirrors `TeacherClient` pattern). Body uses `prompt=template["prefix"]` not `messages=[...]`. Adds `stop: [template["assistant_end"]]` as a soft hint to the server (Ollama / vLLM / llama.cpp / our own --serve all honour it; OpenAI-compat servers that ignore it still parse correctly because the parser strips the marker as belt-and-braces). Same `URLError → RuntimeError("unreachable")`, `HTTPError → RuntimeError("HTTP NNN")`, `JSONDecodeError → RuntimeError("non-JSON")` discipline as `TeacherClient` — failures bubble up so the driver can count and continue.

- **`magpie_collect(*, endpoint, model, n, tag, template_name="chatml", ..., resume=False) -> dict`:** generates `n` independent pairs. Resume keys off `_prompt_key(instruction)` (SHA-256[:16] of the model-generated instruction) so re-running with `--resume` skips instructions already in the JSONL. Duplicates from the same run (model resamples a popular question) are also dropped — Magpie can converge on a few attractors at low temperature, dedup prevents corpus bias toward those. Failures are logged + counted, never abort. **High-failure-rate warning:** if `failed/n > 0.5` after the loop, logs a WARNING naming `--template` as the likely cause — without that signal a user with the wrong template watches a 30-minute run produce 200 zero-row failures with no actionable hint.

- **CLI mutual exclusion:** `--magpie N` and `--prompts FILE` cannot coexist (different paradigms — Magpie generates, prompts mode reads). Either is required. `parser.error()` rejects both `--magpie + --prompts` and neither-supplied, with messages naming both flags so the user sees the choice.
